Voici une réponse concrète, courte et pragmatique pour éviter d'exposer `DataBlock` partout tout en restant efficace sur un CR très volumineux.

Résumé de la stratégie
- Construire et maintenir des index/structures légères (ex : map regionId -> liste d'ids d'unités) lors du parsing du CR. Evite de parcourir la chaîne à chaque requête.
- Garder la source de vérité (les `DataBlock`) dans `CRDocument`. Ne modifiez les `DataBlock` qu'au moment d'écrire le CR ; pour l'édition garder un overlay/delta (vous avez déjà `OrdersDocument` — même idée).
- Exposer aux ViewModels des objets légers (DTO) contenant juste les champs nécessaires (id, name, coords, faction, confirmed). Créer ces DTO à la demande (ou en batch pour la région affichée) et les jeter ou les mettre en cache LRU.
- UI virtualization : ne créer des ViewModels que pour les éléments visibles (quelques dizaines), pas tous les milliers.
- Si vous avez besoin d'accès fréquent mais limité en mémoire : stocker seulement des index (ints+strings) et résoudre `DataBlock` via lookup à la demande.

Exemples de code (minimaux)

1) Indexer les units par région dans `CRDocument`
```csharp
// add field
public Dictionary<int, List<int>> UnitsByRegion { get; } = new();

// call this when vous enregistrez / parsez une unit block
public void IndexUnit(DataBlock unit)
{
    int id = unit.GetId();
    Units[id] = unit; // déjà présent dans votre code existant

    int regionId = unit.ValueInt(KeyType.REGION, -1);
    if (regionId <= 0) return;

    if (!UnitsByRegion.TryGetValue(regionId, out var list))
    {
        list = new List<int>();
        UnitsByRegion[regionId] = list;
    }
    list.Add(id);
}

// helper pour récupérer les ids d'unités d'une région rapidement
public IReadOnlyList<int> GetUnitIdsInRegion(int regionId)
{
    return UnitsByRegion.TryGetValue(regionId, out var list) ? list : Array.Empty<int>();
}

// helper pour récupérer les DataBlock (si nécessaire)
public IEnumerable<DataBlock> GetUnitBlocksInRegion(int regionId)
{
    if (!UnitsByRegion.TryGetValue(regionId, out var ids)) yield break;
    foreach (var id in ids)
    {
        if (Units.TryGetValue(id, out var blk)) yield return blk;
    }
}
```

2) Factory qui crée des ViewModel/DTO légers (pas de DataBlock stocké)
```csharp
using CommunityToolkit.Mvvm.ComponentModel;
using Odyssey.Models.Documents;
using static Odyssey.Models.Documents.CRDocument;

public partial class UnitViewModel : ObservableObject
{
    public int Id { get; }
    [ObservableProperty] private string _name = string.Empty;
    [ObservableProperty] private int _factionId;
    [ObservableProperty] private bool _isConfirmed;
    [ObservableProperty] private int _x;
    [ObservableProperty] private int _y;

    private UnitViewModel(int id) { Id = id; }

    // Factory qui lit le DataBlock et extrait uniquement les champs utiles
    public static UnitViewModel FromDocument(CRDocument doc, int unitId)
    {
        var vm = new UnitViewModel(unitId);
        if (doc.Units.TryGetValue(unitId, out var block))
        {
            vm._name = block.GetUILabel() ?? string.Empty;
            vm._factionId = block.ValueInt(KeyType.FACTION, 0);
            vm._isConfirmed = block.ValueInt(KeyType.ORDERS_CONFIRMED, 0) != 0;
            vm._x = block.ValueInt(KeyType.COORDX, 0);
            vm._y = block.ValueInt(KeyType.COORDY, 0);
        }
        return vm;
    }

    public override string ToString() => $"{_name} ({Id})";
}
```

Points d'architecture / gotchas
- Cohérence index/blocks : tenir les index à jour à chaque modification du `Blocks` ou lors du reparse complet. Si vous appliquez seulement un overlay pour les ordres, l'index n'a pas besoin de changer.
- Mémoire vs CPU : les index accélèrent les lectures (coût mémoire O(n ids) avec des listes d'int). Un int par lien est très peu coûteux comparé à stocker des objets complets. Pour un million d'unités, 1M * 4 bytes ≈ 4MB + overhead listes — mesurable mais souvent acceptable.
- Virtualisation UI : crucial. Ne pas remplir un ObservableCollection avec des milliers d'objets ViewModel si la vue n'en montre que 50.
- Lazy vs eager : factory `FromDocument` copie quelques champs (string peut coûter). Si le nom est la seule string lourde, pensez à stocker seulement un id + short label pré-calculé (ou interned) et charger les autres champs à la demande.
- Caching : utiliser un cache à capacité limitée (LRU) si vous recréez souvent les mêmes UnitViewModels ; utilisez WeakReference si vous voulez laisser le GC libérer quand nécessaire.
- Sauvegarde : conservez votre overlay/delta pour commandes et n'écrasez le CR original qu'à l'export/sauvegarde. Cela évite de toucher `DataBlock` en lecture/édition quotidienne.
- Thread-safety : si parsing / UI occurrent, protégez vos index (`ConcurrentDictionary` ou locks) ou construisez-les avant d'exposer le document à l'UI.

```csharp
// add fields near other dictionaries
public Dictionary<int, List<int>> UnitsByRegion { get; } = new();
public Dictionary<(KeyType key, int value), List<int>> UnitsByKey { get; } = new();

// call from parsing/indexing routine for each unit block
public void IndexUnit(DataBlock unit)
{
    int id = unit.GetId();
    Units[id] = unit;

    int regionId = unit.ValueInt(KeyType.REGION, -1);
    if (regionId > 0)
    {
        if (!UnitsByRegion.TryGetValue(regionId, out var list)) { list = new List<int>(); UnitsByRegion[regionId] = list; }
        list.Add(id);
    }

    // common container keys: BUILDING, SHIP, OWNER, maybe CONTAINER etc.
    foreach (var kt in new[] { KeyType.BUILDING, KeyType.SHIP, KeyType.OWNER })
    {
        int v = unit.ValueInt(kt, -1);
        if (v > 0)
        {
            var key = (kt, v);
            if (!UnitsByKey.TryGetValue(key, out var lst)) { lst = new List<int>(); UnitsByKey[key] = lst; }
            lst.Add(id);
        }
    }
}

public IReadOnlyList<int> GetUnitIdsInRegion(int regionId)
    => UnitsByRegion.TryGetValue(regionId, out var l) ? l : Array.Empty<int>();

public IReadOnlyList<int> GetUnitIdsByKey(KeyType key, int value)
    => UnitsByKey.TryGetValue((key, value), out var l) ? l : Array.Empty<int>();
```

Gotchas et conseils pratiques
- Index maintenance : remplir les index à la lecture/parse du CR. Si le CR est ré‑parsé, rebuild. Si tu modifies réellement la structure (rare), mets à jour l’index en conséquence.  
- Mémoire vs CPU : index de type List<int> est très rentable. Pour des millions d’éléments, tu peux compacter/stocker en arrays ou pages.  
- UI virtualisation : ne créer que les ViewModels visibles (load on expand / virtualization). Ne mets pas des milliers d’ObservableCollection éléments en mémoire si inutile.  
- Chaîne source (DataBlock) : conserve‑la pour l’écriture finale et pour opérations détaillées (items, talents). Pour la plupart des vues, un DTO léger suffit.  
- Concurrence : si parsing est fait en background, protège les index ou expose une snapshot immuable au UI thread.
